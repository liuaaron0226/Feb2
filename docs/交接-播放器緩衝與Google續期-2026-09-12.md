## 4. 現在的架構與已做過的修正

### 影片與教材

- Cloudflare Pages 提供網站、字幕、索引、講義與思考地圖。
- 影片在私人 Google Drive。
- 桌面可由 `<video src="/drive/<id>">` 交給 Service Worker 取得 Google 的 Range 回應。
- iPad／iPhone 的既有路徑是 JavaScript fetch fragmented MP4，交給 MediaSource／ManagedMediaSource 的 SourceBuffer。
- `.fragidx.json` 走網站的 `/data/sidecars/`；`.frag.mp4` 走 Google。**Drive 上字幕備份較舊，不代表網站正在顯示舊字幕。**
- 網站與影片 Google 授權是兩道不同的門。能開網站，不等於持有有效 Drive token。

### 上一版已做過，不要再當成尚未修的發現

`14-drive.js` 現有重要符號：

- `driveRead()`：等待涵蓋 response body，支援 AbortSignal；預設 30 秒，大段下載約 30～60 秒逾時。
- `DRIVE_STREAMS`、`driveMSEAttach()`、`driveMSEDetach()`、`driveMSERecover()`：每個 video 獨立管理下載、事件、計時器與 blob。
- `holding`、`hold()`、`releaseBuffer()`：高倍速緩衝不足時保留播放意圖，先暫停累積再恢復。
- `reserve()`：目前約 `8 × playbackRate` 秒媒體時間；3 倍約 24 秒影片，等於 8 秒實際播放。
- 前向 horizon：隨倍率增加，最多 120 秒媒體時間，另用約 24 MiB 的估算上限約束。
- 每批最多 4 個連續片段、2 MiB；低緩衝或重試有退回單片段的條件。
- MMS 的 `endstreaming` 會停止預取；若正處於 holding，會解除軟體暫停，避免等不到系統不允許的 reserve。
- 尾段載完、MediaSource 已 ended 後再往前 seek，會重建串流。
- `driveAuth()`：共用 pending、序號隔離舊回覆；逾時後有效晚到 token 可接收，但不能蓋掉新的授權。
- `driveTokenAsk(force)`／SW force refresh：Google 回 401 時不再只是重送相同舊 token。

`10-player.js` 已補：

- `PLAYER_LOAD` 防止舊非同步結果覆蓋新影片。
- 初次載入失敗後重試仍保留原本存檔位置。
- 引擎恢復期間不將 0 秒寫回觀看進度。
- 恢復期間按暫停，以最新意圖為準，不再自動蓋回播放。
- 暫停鍵能取消 holding 的待播放意圖。

## 5. 每小時授權：應優先處理的架構問題

### 5.1 已確認的限制

目前前端使用 Google Identity Services 的 `initTokenClient()`，scope 為 `drive.readonly`。這是 **Token model**，前端拿到的是短效 access token，不是可由後端長期使用的 refresh token。

Google 官方說明：Token model 的授權更新需要使用者在場並互動；需要背景更新時，應使用 Authorization code model。Safari 的 cookie／彈窗／使用者手勢限制，使得把 `driveAuth(true)` 當作可靠背景續期尤其不穩。

因此，不可再用以下方式宣稱解決：

- 每 50 分鐘呼叫一次 `initTokenClient()` 就保證不彈提示。
- 修改 `DRIVE.exp`，假裝 Google 簽發的 token 活得更久。
- 把 access token 永久寫入 localStorage。
- 要求關閉跨網站追蹤防護，當作產品的必要操作。
- 每次重新整理都強制 `prompt=consent`。

### 5.2 推薦方案：後端只管理授權，不代理影片

建議沿用既有 Pages Functions 與 D1，新增 OAuth authorization-code 的離線授權流程。

概念流程：

1. 使用者在 Feb 按一次「連結 Google」。
2. 後端建立一次性 state、必要的 PKCE 與 session 綁定，導向 Google 授權。
3. callback 驗證 state／session，後端交換 code；要求 offline access。
4. 後端確認這是允許的 Google 帳戶，將 refresh token **加密後**保存。
5. 播放器透過自己的受保護端點取得短效 access token。
6. access token 快到期時，後端使用 refresh token 更新，正常情況不需要使用者重新點 Google。
7. 影片 Range 仍由瀏覽器帶短效 token **直接請求 Google**。

這是新增方案，不是 repo 已有功能。實作前要確認站台身分驗證能安全支撐長期 Drive 授權；不能只新增一個誰都能呼叫的 `/token`。

### 5.3 後端端點草案與權限

以下路由名稱是建議，可配合專案慣例調整：

| 建議端點 | 行為 |
|---|---|
| `POST /api/drive/connect` | 已驗證 owner 發起連結，建立短效一次性 state／PKCE |
| `GET /api/drive/callback` | 驗 state、session、code 與帳戶身分；交換並保存憑證 |
| `POST /api/drive/token` | 驗證 owner，回傳尚有效或已續期的短效 access token |
| `GET /api/drive/status` | 只回 connected／needs_reconnect 等狀態，不含秘密 |
| `POST /api/drive/disconnect` | 明確使用者動作後解除網站持有的授權；不要自動撤銷所有 Google 授權 |

最低安全要求：

- 每個敏感端點檢查伺服器已驗證的身分與 `role === owner`。guest 不得取得任何 Drive token。
- 現有 middleware 可能走 Access，也可能走通行碼；先查實際啟用方式，不能假設一定是 Access。
- 通行碼分支中的 owner 身分不等於已核實 Google 帳戶。Google callback 必須另核對允許的 Google 帳戶，不能把任意登入帳戶綁進去。
- 若用 OIDC，驗證 issuer、audience、簽章、有效期與 subject；或採官方支援且可驗證的伺服器端帳戶資訊流程。不要自己手刻不完整 JWT 驗證。
- `state` 不可預測、一次性、短有效期，與發起者綁定。callback 重播、錯誤 state、錯誤 session、錯誤帳戶均拒絕。
- 選定 Google 官方支援的流程後落實 PKCE／client secret 等要求，不混用不同流程的參數。
- redirect URI 必須在 Google Console 精確登記正式 HTTPS 網址，不使用任意 redirect、wildcard 或未授權 preview 網域。
- POST 做同源／CSRF 防護；callback 的 state 與 cookie 設計需能支援 Google 頂層導回，不可為了跑通而全面放寬 cookie 或 middleware。
- token 回應設 `Cache-Control: private, no-store`；不允許任意 CORS。
- SW 不得把 token／OAuth API 回應放進 Cache Storage。
- 記錄錯誤時只留階段、狀態碼與安全代號，不能留下 code、token、cookie、Authorization 標頭或 callback 完整網址。

### 5.4 憑證保存與設定

優先利用既有 binding `DB`（D1），另建小型專用資料表，**不要重建或清空現有進度資料表**。

建議保存 owner 鍵、Google 帳戶識別、加密 refresh token、token 到期資訊、版本／續期租約等必要欄位。

- refresh token 在寫入 D1 前，以標準認證加密方式加密，例如 Web Crypto AES-GCM；每次使用新的隨機 nonce，妥善處理版本與 key rotation。
- 加密金鑰與 OAuth client secret 存 Cloudflare **Secrets**，不存同一張 D1 表或前端設定檔。
- 可用名稱例如 `GOOGLE_OAUTH_CLIENT_ID`、`GOOGLE_OAUTH_CLIENT_SECRET`、`DRIVE_TOKEN_ENCRYPTION_KEY`；名稱是建議，值不得進文件。
- 現有 `data/drive-client.json` 最多保留公開 client ID，不能塞秘密。
- 若儲存 access token 以供多裝置共用，也按敏感憑證處理，不能明文散落於報表。
- Google 續期成功但未回傳新的 refresh token 時，**保留舊的**，不能寫成 null。
- 避免手機和平板同時過期造成續期風暴；後端多個 isolate 不能只靠全域 JS Promise 當分散式鎖。用既有儲存設計短效 lease／CAS，失敗可回收，不要建立永遠不釋放的鎖。
- `invalid_grant`／確定撤銷與暫時網路錯誤、429、5xx 必須區分。暫時故障不應刪掉有效 refresh token 或強迫再次同意。

Cloudflare 控制台或 CLI 的 Secrets 操作需由使用者授權；先確認現有設定名稱，不讀出／印出 secret 值。新增資料表前備妥安全備份與回復方式，不用破壞性 migration。

### 5.5 Google Console 必查陷阱

1. 網站的 OAuth 用戶端與 `gws` CLI 不同。只修改網站對應的正確專案／用戶端。
2. Drive API 曾未啟用，已在先前處理，當時實際 Range 由403轉206。不要看到任何403就重做同一套。
3. 查 OAuth consent screen 的 User type 與 Publishing status。
4. **External＋Testing 的 refresh token 通常7天到期**；Drive scope 不屬於只含基本姓名／email／profile 的例外。
5. 不可未經確認就切 Production；先查 Google 目前的 scope 分級、個人用途例外、驗證要求與使用者限制。
6. offline access／refresh token 的取得條件要按官方流程設好。既有同意不保證每次 code exchange 都回新的 refresh token。
7. 只有確實需要重新同意時才使用相應流程；不要每次自動 `prompt=consent`，更不要擅自撤銷既有全部授權。
8. Google Pro 的5TB是容量，不保證私人Drive可作無限制高效能CDN。

### 5.6 從現在模式遷移，不能讓原使用者突然不能上課

- 先完成後端與測試，再切換前端。
- 首次遷移可能需要使用者按一次新的連結／同意；明確說明這是切換到背景續期，不是每小時都要做。
- 後端未設定齊全時，不要把已能用的舊播放器直接砍掉；保留明確過渡退路與可回復版本。
- 帳本鍵、影片URL與進度鍵不要因OAuth切換而改掉。`PL_LS` 目前以穩定的影片ASSET URL為鍵。
- 若真的必須換鍵，先做可驗證且冪等的舊資料遷移，禁止讓使用者從空進度開始。
- 正常access token更新不重建整份播放器、不跳回片頭、不改倍速，也不打斷仍可播放的緩衝。

### 5.7 前端具體接線，避免後端做完卻沒有用到

- 在 `functions/api/drive/` 與 `functions/_lib/` 按現有檔案慣例實作端點與憑證模組；新增測試及可回復的資料表 migration，不擅自改進度合併邏輯。
- `14-drive.js` 的背景 `driveAuth(true)` 改向自己的受保護 token 端點取短效權杖；互動連結則走新 connect 流程。保留清楚的函式契約，不能一半呼叫舊 GIS、一半呼叫新後端而互相覆蓋。
- 以伺服器回傳的有效期建立本機期限，預留合理安全餘裕；播放前、每批 Range 前、回到前景與 online 後都檢查。不可只靠整點計時器，因 iOS 背景可能停止執行 timer。
- 正常取得新短效 token 後，沿用 `driveSetToken()`／`drivePush()` 更新 SW 與正在等待的串流，不更動影片 ASSET URL。
- Google 回401時，只做一次受控的強制更新與重試；後端快取不能把同一張已被拒絕的權杖原樣送回。多裝置請求仍要去重；可比較被拒絕 token 的版本與後端現有版本，避免舊請求迫使新 token 無限重換。
- `/api/drive/status` 明確区分「尚未連結」、「已連結可背景續期」、「需要重新同意」、「暫時連不上」。登入過期、Drive授權撤銷與純網路故障不能共用同一句錯誤。
- 如果保留短效 token 的本機快取，仍不得保存 refresh token；若改成只留記憶體，重新開頁應由後端安全补發短效 token，而不是再次跳 Google 同意畫面。

## 6. 頻繁緩衝：先找瓶頸，不要盲目加參數

### 6.1 必須量測的資料

從使用者真實會看的「電子學09」開始，至少測影片時間約3123秒與4923秒兩處。前者對應3倍時剩約15分鐘的另一種解讀，後者是原影片剩15分鐘。

每5秒彙整一次，避免逐幀／逐chunk刷日誌：

- 實際 `playbackRate`、`currentTime`、`paused`、`seeking`、`readyState`。
- 緩衝的連續範圍與 ahead 秒數；再除以倍率得到實際可播秒數。
- holding 的進出次數、累計等待時間、開始播放前等待時間。
- 每個Range的請求長度、收到headers耗時、body完整讀完耗時、HTTP狀態。
- 傳輸完成的有效bytes／總時間；重試及被取消浪費的bytes要另外計。
- 同時在途請求數、MMS startstreaming／endstreaming、SourceBuffer errors／QuotaExceeded。
- 新影格的呈現時間：優先 `requestVideoFrameCallback` 的 `mediaTime`，配合 decoded／dropped frames；**時間軸有值不能證明畫面有更新。**

不得把真實token、cookies、完整Drive URL／檔案ID混入輸出。以課程代號與請求序號代替。

### 6.2 核心計算

一段媒體長度為 `D` 秒、大小為 `B` bytes、播放倍率為 `R`：

- 播完它所需牆鐘時間 = `D / R`。
- 平均必要有效下載速率 ≈ `B × R / D` bytes/s。

若實測body完成時間持續大於 `D / R`，就會消耗既有緩衝。加大緩衝只能延後卡頓，不能讓長期平均不足的頻寬憑空增加。

先前例子：某些約8秒的片段需3～5秒下載；3倍只需約2.7秒就播完。這是當次測量，不是現在網路的固定上限，需重測。

### 6.3 依量測結果選擇修法

**A. 主要是每次請求延遲／逐段序列的空轉**

- 比較現行單段、現行合併2MiB、適量更大但有上限的合併請求。
- 分清headers快、body慢，不能只量 `await fetch()`。
- 評估在同一條下載回應內逐步餵入完整片段，避免等整批arrayBuffer讀完才開始append。
- 若評估最多2條預取流水線，必須先量單線／雙線的總有效速率；不要先宣稱一定加倍。
- 網路讀取可以重疊，SourceBuffer更新仍須序列化。
- seek／取消時以generation與AbortSignal一起處理，舊資料不得在新位置後append。
- 不多開現有整庫上傳器來測播放器速度；那是另一條路且有共用帳本鎖。

**B. 主要是holding策略自己造成反覆停播**

- 測量入門檻與出門檻是否有足夠遲滯，避免剛恢復立即又被暫停。
- 不因每個ratechange／playing／waiting事件都無條件重新hold。
- 使用者按暫停要取消待播放意圖；恢復或新授權不准自動違背最新選擇。
- MMS可用緩衝由瀏覽器決定，不能用一般MediaSource測試推論Safari一定允許累積到reserve。
- 複驗「holding但未達reserve時收到endstreaming」不會互等。
- 媒體buffer秒數與3倍實際播放秒數分開記，避免把120秒影片寫成120秒可觀看時間。

**C. 主要是3倍解碼／裝置負載**

- 在受控、已充分緩衝的條件測3倍；如果仍掉幀或影格不前進，再查解碼與UI負載。
- 查真正可見的video、背景影片、字幕／圖表更新與重複事件；不要看到大JS就直接重寫。
- 不把固定長時間未收到frame callback直接判成故障：背景／遮擋時callback可能被節流。
- 要測iPad Safari的真實ManagedMediaSource，不只Chromium的模擬事件。

**D. 持續有效下載速率確實低於所需**

使用者沒有更快網路。此時應誠實提出取捨，不能繼續承諾光調JS就全程3倍不卡：

- 較長的起播預緩衝，只改善短暫波動，說清楚等待代價。
- 必要時評估額外的低位元率「串流副本」。先選電子09的一小段做視覺比較，確保板書、上下標與公式可讀，再向使用者確認；不可直接全庫壓縮、覆蓋原片或降低畫質。
- 優先評估保留板書解析度下的編碼／影格率取捨；不要直接降到看不清文字的解析度。
- `ffmpeg -c copy` 只是重封裝，不會解決位元率太高。
- 新副本若獲准，須重新產生對應索引並核對大小／offset，先一堂通過再談批次。

## 7. 分段實作與紅綠測試順序

一次一個行為切片，不要先寫完所有功能再用測試包裝成功。

### 第一段：建立基準，不改行為

1. 確認實際檔案／正式版本與目前使用裝置。
2. 用電子09重現緩衝、續播、網路恢復。
3. 保存有時間戳的安全統計，不輸出憑證。
4. 先確定是下載、解碼、hold策略或授權等待占比最大。

### 第二段：後端離線續期

先完成隔離測試，涵蓋：

- 未登入與guest不能取得token或發起owner綁定。
- state不符、callback重播、錯誤Google帳戶全部拒絕。
- 首次取得refresh token後能在access token過期時更新。
- 續期回應不帶新refresh token時保留原值。
- 多裝置同時更新不發生無限制重複請求。
- 暫時503／429不會刪掉長期憑證。
- 確定invalid_grant時清楚顯示需要重新連結，沒有無限彈窗或無限重試。
- 舊回覆不蓋新token；續期後同一video位置與倍率不變。
- refresh token與client secret從不出現在HTML、JSON資產、API回應、Cache Storage、日誌或Git diff。

### 第三段：播放器有效吞吐與緩衝

以同一段影片、同一網路條件比較修改前後：

- 每10分鐘卡頓次數與累計等待時間。
- 起播與seek到實際正確影格所需時間。
- 被取消／重傳浪費的bytes。
- 2.5、3倍在連續觀察窗內的實際時間前進量與影格時間。
- 短暫斷線後原頁面恢復，不需要滑掉頁面。

若新策略只是把頻繁卡頓變成一次等很久，不能省略起播等待指標。

### 第四段：長課程與遷移驗收

- 用既有觀看紀錄進入，不建立空使用者冒充遷移成功。
- 確認本機URL／舊雲端URL的進度來源；不同origin的localStorage不會自然互通。
- 先用測試時鐘／受控到期驗證續期，再做真機至少跨兩次access-token更新的長測。
- 理想以使用者的一堂3小時以上課程驗證；報告實際測了多久，不能把6秒測試寫成整堂穩定。
- 無法取得真機時，列明尚未驗證，不能宣布問題完全解決。
